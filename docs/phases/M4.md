# M4: Wall back end (owner: Grok, Wave B, about 3 days, alongside M2)

> Paste `docs/RULES.md`, then the phone rules block in `docs/phases/PHONE.md` § 3, then this file, as the first message in the coder's session. Before coding, read `AGENTS.md`, `docs/PLAN.md` § Satus adaptations (§ E5 covers the phone layout) and `docs/phases/PHONE.md`.

**Depends on:** M1 (contract) and M3 step 1 (`wallPhotos`).

**Build order:**

1. **`POST /api/v1/wall`:**
   1. Parse the request with the contract.
   2. Verify ALTCHA with the existing verifier.
   3. Replay a repeated `Idempotency-Key`, the way leads do.
   4. Rate-limit at 3 posts an hour per address, with `lib/utils/rate-limit` (or P8's limiter, if P8 has landed).
   5. Reject anything over 8 MB with `413`.
   6. Detect the type from the file's bytes (JPEG, PNG, WebP or HEIC); anything else gets `415`.
   7. With sharp, apply `.rotate()` to honour orientation, then re-encode to WebP at no more than 1600 px. This **drops all metadata, including GPS**.
   8. Create the record as pending through the Local API, storing only a hash of the removal token.
   9. Answer `202`.
2. **`GET /api/v1/wall`:** approved photos only, newest first, 30 a page, cached briefly and tagged for revalidation.
3. **`POST /api/v1/wall/report`:** adds a report, once per visitor and photo, and answers `204`. At three reports the photo returns to pending, which hides it. It's rate-limited.
4. **`POST /api/v1/wall/remove`:** a constant-time token check, then status removed and the file deleted, answering `204`. Anything wrong answers `404`.
5. **A daily worker job:** delete rejected photos older than 30 days, and any orphaned files.
6. **Logs** never contain images, tokens, names or consent text.
7. **Tests** (`bun test`, handlers through `getResponse`):
   - every status code in the contract;
   - an idempotent replay;
   - a fixture photo with GPS EXIF comes out with no metadata;
   - token checks;
   - type sniffing.

**Acceptance criteria**

- Every status in the contract can be reached.
- Stored files have no EXIF or GPS.
- A pending file can't be fetched by URL.
- Going over the rate limit gives `429`.
- A double submit creates one record.
- `bun run check` passes.

**Handoff notes for M9**

- **Storage.** Wall files go in `WALL_MEDIA_DIR`, default `./.data/wall`, and that path must stay outside `public/`. The Compose `web` and `worker` services do not mount it, so recreating a container drops the files while the rows remain. Give both services one persistent volume, and decide whether backups copy that directory. `deploy/backup.sh` dumps Postgres only.
- **Upload size.** Caddy is the edge proxy. A post is an 8 MB photo plus the multipart fields (consent text, ALTCHA, name), which stays under 9 MB. The Caddyfile does not set a body cap today. If M9 adds `request_body { max_size … }`, use at least `9MB`.
- **Schedule.** `wall.purge` runs daily at 03:15 UTC. It deletes rejected photos whose status changed more than 30 days ago, files in the wall directory that no row names and that are older than one hour, and `integration.wall_posts` receipts older than 24 hours. Those receipts are the only copy of the raw removal token.
