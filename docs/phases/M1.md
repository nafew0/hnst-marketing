> Paste `docs/RULES.md`, then the phone rules block in `docs/phases/PHONE.md` § 3, then this file, as the first message in the coder's session. Before coding, read `AGENTS.md`, `docs/PLAN.md` § Satus adaptations (§ E5 covers the phone layout) and `docs/phases/PHONE.md`.

**Depends on:** `main` as of 6 Nov (P1–P7 and P7W).
**Nafew provides before start:** nothing.

**Build order:**

1. **Spike, then report to Nafew before continuing.**
   - A server-rendered home screen on `/` under 800 px: wallpaper poster, three icons and the dock.
   - Open and close Calendar (`/book`) through P7W's window route, with a rough phone skin: the zoom from its icon, Back, Esc and a home bar.
   - Visit `/book` directly at phone size, and load `/` with JavaScript off.
   - In the browser at phone sizes (375 × 812, 390 × 844, 430 × 932), in WebKit and Chromium emulation, test:
     - safe areas and `100dvh`;
     - Back and the home bar;
     - the layout with the browser's own bars in mind.

     Real phones are not used (Nafew, 6 Nov). What emulation can't show, such as iOS's own edge swipes or a real Safari toolbar, is listed in the report as untested.

   - The report says what works and what the plan should change. **No LCP measurement.**
2. **The app registry** (`components/ui/phone/registry.ts`).
   - Each app has an id, label, accessible name, icon, place (grid or dock), owner and kind: a route URL, a phone-only `?app=` view, or an external link.
   - Phone-only apps (Camera, Notes) lazily load `components/apps/<id>/index.tsx`, at `/?app=<id>`. M1 creates a placeholder for each, so their owners only replace them. Content apps keep their pages; how each gets its phone view is M2's (§ M2 step 5).
   - The desktop dock keeps its current list. Nothing on desktop changes.
3. **The wall contract** (`lib/contracts/wall.ts`). It adds to v1 and changes nothing that exists; it was approved with the public-wall decision.

   | Route                      | Request                                                                                                                        | Answers                                                                           |
   | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
   | `POST /api/v1/wall`        | multipart: `image`, `consentText`, `adult: true`, optional `displayName` (≤ 40 characters), `altcha`; `Idempotency-Key` header | `202 { status: 'pending', id, removeToken }`; `400`, `413`, `415`, `429`          |
   | `GET /api/v1/wall?cursor=` | —                                                                                                                              | `200 { items: [{ id, src, width, height, displayName, createdAt }], nextCursor }` |
   | `POST /api/v1/wall/report` | `{ id }`                                                                                                                       | `204`; `400`, `404`, `429`                                                        |
   | `POST /api/v1/wall/remove` | `{ id, token }`                                                                                                                | `204`; `400`; `404` for a wrong id or token (never says which); `429`             |
   - Errors use the usual `{ error: { code, message, fields? } }`. `413` and `415` are `validation_failed` with `fields.image`. A repeated `Idempotency-Key` replays the first response.
   - A photo's public `id` is a UUID, never the database id.
   - Add MSW handlers with magic values for every status, regenerate `openapi.json`, and pass `contracts:check`.

4. **CMS shapes for Astra** (`components/ui/phone/settings.ts`): the Zod schema of the phone fields in site settings, with DRAFT copy for when the CMS has none.
   - **The notifications list:** a trigger, the app it opens, title, body and an on/off switch. The triggers are `lock-first-visit`, `home-idle`, `left-packages`, `photo-taken`, `booking-queued`, `booking-confirmed`, `wall-sent` and `ebook-ready`.
   - **Copy fields:** the widget copy, the camera frame text, the wall consent text, the wall rules link and a lock-screen on/off switch.
5. **Shared config:**
   - `Permissions-Policy` becomes `camera=(self)`.
   - Add the flag `NEXT_PUBLIC_PHONE_LAYOUT` (`'1'` = on). The phone layout is off by default until M9, so `main` stays releasable while it's built.
   - Add `WALL_MEDIA_DIR` (server only, default `./.data/wall`, git-ignored) to `lib/env.ts` and `.env.example`.
   - Add `CODEOWNERS` entries for § 4's paths.
   - Brand tokens only if a phone surface truly needs one.
6. **Docs:** copy this file's briefs into `docs/phases/M1.md`–`M9.md`, and add `docs/PLAN.md` § E5 "Phone layout".
